# PawTrader functionality, usability, and live-readiness review

Date: 2026-09-06. Brain revision: `58901b6`.

## Assessment

Keep paper trading while repairing execution and evaluation. PawTrader now has fill reconciliation, exits, deduplication, risk sizing, and substantial tests. However, the current implementation cannot reliably establish that it is ready to earn money with live capital. Bitcoin execution is incomplete, the readiness statistic is incorrect, and dashboard accounting differs from the readiness calculation. More trades or lower approval thresholds would not resolve these defects.

Scope: targeted review of `src/trader`, trader HTTP routes, dashboard rendering/polling, local trader DB aggregates, and the companion `<trader-engine>` source. This is not an exhaustive audit of every ClaudePaw subsystem. No trading config, production state, orders, or implementation files were changed.

## Findings, ordered by priority

### 1. P1: Bitcoin signals cannot complete the advertised execution path

Evidence: `trader-engine/src/trader_engine/api/main.py:57` and `:76` retain only an `AlpacaAdapter` as the execution adapter. The Coinbase adapter created at `:137` is used for a connectivity probe. `api/routes/decisions.py:122` always resolves that Alpaca adapter; it has no per-asset routing. `execution/alpaca_adapter.py:193` and `:209` use `TimeInForce.DAY` for entries, including fractional orders.

Alpaca crypto permits GTC/IOC, not DAY ([official crypto-order contract](https://docs.alpaca.markets/us/docs/crypto-orders)). The Coinbase adapter's existence and green connectivity flag therefore do not establish a working Bitcoin execution route. The historical `/prices/{asset}` endpoint also uses an equity data client and a non-path parameter, so slash-containing crypto symbols need a separate contract review (`api/routes/prices.py:19`, `:45`).

Fix: explicitly select an execution venue and mode per asset class. For the first Bitcoin paper workflow, Alpaca crypto paper is a candidate already supported by the vendor; implement its order types, precision, fees, market data, reconciliation, and exit lifecycle end to end. If Coinbase is the intended live venue, use a matching local paper adapter and validate its production contract independently. Coinbase's current Advanced Trade sandbox returns static responses; it is not a realistic paper trading simulator ([official sandbox docs](https://docs.cdp.coinbase.com/coinbase-app/advanced-trade-apis/sandbox)). Keep the crypto strategy paused until this workflow passes.

Acceptance: a simulated BTC entry -> partial fill -> full fill -> protected hold -> exit -> fee-adjusted P&L completes through the real application interfaces, including weekends and restarts. UI identifies venue, asset class, and paper/live mode separately.

### 2. P1: The statistical readiness calculation is mathematically wrong

Evidence: `src/trader/metrics.ts:241` evaluates inverse-normal CDF at zero when `trials=1`, producing negative infinity and hence DSR=1 for any otherwise valid sample. At `:243`, the expected-maximum term also omits the scale derived from the variance of trial Sharpe estimates. This input is part of the published method ([Bailey and Lopez de Prado, equations 1-3](https://www.davidhbailey.com/dhbpapers/deflated-sharpe.pdf)). The current function has no trial-variance input.

Reproduced without external calls: 100 alternating returns of -0.01 and +0.01001 produce Sharpe 0.007933 and DSR **1.0** for one trial; the same series produces approximately **6.49e-26** for four trials. The stored four-variant failure cannot be treated as a calibrated probability of no edge. Correcting the formula does not establish that the current strategy will pass.

Fix: validate the implementation against independent published/reference cases, handle a single trial with a finite benchmark, record trial history and its variance, and explicitly define return frequency. Current Sharpe annualizes per-lot returns with sqrt(252), despite variable holding periods and overlapping positions (`validation-gate.ts:113`, `metrics.ts:66`). Use daily portfolio returns for annualized portfolio metrics and retain trade-level expectancy as a separate measure.

Acceptance: weak one-trial evidence stays near uncertainty, known reference results match, and changing only lot splitting cannot improve confidence.

### 3. P1: Readiness can pass without necessary validation evidence

Evidence: `go-live-gate.ts:219` catches missing NAV history and continues with an empty curve. `validation-gate.ts:144` accepts the resulting zero drawdown. An in-memory evaluation with 136 alternating -1%/+2% returns, one variant, a positive backtest, and **no equity history passed the entire gate**.

Other unsupported assurances: `go-live-gate.ts:278` hardcodes `outOfSampleNoRetune: true`; `:149` accumulates regimes observed on gate runs rather than regimes attached to actual trades; `:208` aggregates the full fill history while `:258` compares it to the current momentum backtest. There is no matching strategy/config version and evaluation start boundary. `trader-scheduler.ts:442` trusts any persisted `passed` result without expiry or a config fingerprint. If weekly reevaluation fails, a historical pass remains valid.

Fix: use immutable evaluation cohorts identified by strategy version, risk/exit parameters, venue, mode, cost model, and date window. Require complete finite NAV data and trade-linked regimes. Invalidate readiness on config changes, stale evidence, or reconciliation failures. Treat missing evidence as unknown/blocked. Enforce live eligibility at order submission as well as in the scheduler; if a halt request fails, the scheduler must still block entries locally.

Acceptance: missing NAV, stale gate, changed strategy, unmatched backtest, and unsupported out-of-sample assertions each block readiness. A previously passed result cannot authorize a new strategy version.

### 4. P1: Retrying an order removes its protection and changes its intent

Evidence: `order-retry.ts:65` does not load entry, stop, target, or strategy. The submit payload at `:101` sends `entry_price: 0`, `strategy: ''`, and no stop/target. In-memory reproduction started with entry 100, stop 92, and target 116; the retry sent none of those prices. The engine consequently constructs a simple unprotected entry.

The same path lacks signal age and paused-strategy checks. Recovery resets state but not the attempt budget (`:54`, `:95`): a three-attempt order goes engine_down -> retry_pending -> engine_down forever. Reproduced for two healthy sweeps. The local DB contains 14 matching stuck rows.

Fix: persist a complete immutable order intent and preserve it through retries. Reconcile ambiguous outcomes by stable identity; revalidate age, strategy status, and risk before any legitimate resend. Distinguish recoverable outage, expired signal, and exhausted/terminal order. Do not merely reset all old attempt counts: that could submit obsolete July decisions.

Acceptance: retry preserves exits and identity; paused or expired entries never resubmit; recovery terminates or resumes explicitly instead of cycling indefinitely.

### 5. P1: Broker submission is not idempotent at the engine boundary

Evidence: `trader-engine/src/trader_engine/api/routes/decisions.py:245` generates a new UUID on every submit, without returning an existing order for the same decision. `:283` times out an `asyncio.to_thread` operation and marks its row failed at `:290`, although timing out the await does not stop the underlying broker call. A late broker acceptance followed by another submission can therefore produce two orders. The brain's 100-order snapshot check reduces risk but does not supply atomic engine idempotency.

Fix: stable idempotency key per order intent, an enforced unique reservation, payload conflict detection, and an explicit unknown-submission state until broker lookup resolves the outcome. Do not call an ambiguous timeout a confirmed failure.

Acceptance: simultaneous duplicate requests and a broker ACK arriving after the caller timeout create exactly one broker order and retain its original protections.

### 6. P1: Dashboard P&L disagrees with the gate and is not a complete cost-adjusted ledger

Evidence: `server/src/trader-routes/status.ts:287` reads only `/orders`; the engine caps that endpoint at 100 rows (`api/routes/orders.py:51`). Older buys vanish, leaving unmatched sells ignored by FIFO. Meanwhile the gate merges historical `trader_fills` (`go-live-gate.ts:88`). Identically labeled “broker truth” can therefore disagree or change when an old order rolls out of the window.

`go-live-gate.ts:74` also zeroes fees and slippage for recent engine orders, replacing any richer historical fill for that order. Its recent-order filter excludes canceled/expired orders that partially filled (`:58`). `matchLotsFifo` produces one result per lot intersection (`audit-log.ts:155`), and the gate counts these as independent closed trades. Splitting an economic trade into multiple fills can increase its apparent sample count. The Coinbase adapter reports zero cost basis and unrealized P&L (`coinbase_adapter.py:133`).

Fix: one durable, broker-reconciled execution ledger shared by dashboard, reports, and evaluation. Use incremental fills, execution timestamps, real fees, explicit estimated paper costs, and defined economic round trips. Reconcile cash movements and distinguish account equity from strategy return. Alpaca paper does not simulate all live frictions ([paper-trading limitations](https://docs.alpaca.markets/us/docs/paper-trading)); current fee-free paper gains do not establish net live profitability.

Acceptance: identical totals across dashboard/report/gate; history survives order-window rollover; partial-fill cancellation, fee allocation, and multi-fill trade counting have independently calculated expected results.

### 7. P1: Some positions depend on a weak software exit backstop

Evidence: `trader-engine/src/trader_engine/risk/position_sizer.py:99` deliberately drops brackets for sub-share entries. That makes software exits essential. `src/trader/exit-evaluator.ts:229` checks the latest historical daily close without a quote-age check. Its momentum exit reads entry-time enrichment, not current momentum (`:129`). It cannot detect momentum deterioration after entry from an unchanged stored value. Engine circuit breakers reject requests before the sell/close branch (`api/routes/decisions.py:144`, `:175`), so a halt can also prevent software risk-reducing exits.

Fix: make protection status explicit and verify protective orders after each fill. Use fresh executable market data for software exits and recompute momentum from current data. Define halt semantics separately for new entries, cancellation, and risk-reducing closes. A fractional entry needs a supported protective mechanism before it is permitted in live mode.

Acceptance: stale quotes block unsafe actions with a visible alert; partial fills and fractional entries have verified protection; deliberate halt behavior is tested for existing positions as well as new entries.

### 8. P1: An outage looks like safe paper mode and a flat portfolio

Evidence: `_renderKpiEngineCell` at `server/public/app.js:8025` maps missing mode to “unknown,” then renders every non-live value as “Paper.” `/positions` returns `[]` on engine error (`status.ts:77`), which the UI converts to zero unrealized P&L (`app.js:8178`). The realized KPI keeps its old value when new data is unavailable (`:7963`). This can present a paper label, empty holdings, and stale positive returns during an outage.

Fix: model mode and connectivity separately: Paper / Live / Unknown; Connected / Delayed / Offline. Preserve last-known holdings with timestamps and explicit stale labels. Unknown P&L must never become zero. Surface failed reads consistently across cards.

Acceptance: injected status/positions/P&L failures visibly show unknown/stale state without erasing known exposure or suggesting a confirmed paper account.

### 9. P2: Readiness and next steps are buried; the UI explains an older workflow

Evidence: `app.js:7841` appends readiness after the main grid and bypass card; emergency halt is also in the footer. Gate detail is only a title tooltip (`:10146`), and warnings/backtest context are not rendered. The signals KPI adds pending signals and existing decisions (`:8352`) and calls them all “pending.” Help at `:8375` describes every signal going through committee, although deterministic momentum routing exists.

Fix: lead with a persistent status summary: current venue/mode, whether new entries are enabled, actual net result for a labeled period, and the next unmet readiness requirement. Present positions with “why bought / protection / next exit condition.” Separate Ideas, Orders awaiting fill, Holdings, and Closed trades. Put research metrics and committee transcripts in expandable detail. Make Pause new trades distinct from closing positions.

Acceptance: a first-time user can answer “Is real money at risk?”, “What do I own?”, “What is protected?”, “Am I ahead after costs?”, and “Why am I still paper trading?” without tooltips or reading source.

### 10. P2: Duplicated policy and repeated polling increase drift and operating cost

Evidence: FIFO is separately implemented in the brain, dashboard server, and verification script. Position risk also has multiple implementations: the strategy gate supplies `openRiskUsd: 0` (`decision-dispatcher.ts:124`), while another path estimates heat from a default stop distance (`risk-sizing.ts:40`). Those are not an authoritative sum of actual stop risks. Several dashboard sections poll independently every five seconds (`app.js:7879`); server status itself fetches health and reconciliation. The code also processes/enriches candidates before dispatch identifies already-held assets (`trader-scheduler.ts:529`, `decision-dispatcher.ts:619`).

Fix: share financial contracts and computations, maintain a single snapshot per dashboard refresh, cache market history by symbol/timeframe, and aggregate repeated unchanged suppressions. Derive risk from actual open lots, pending orders, and protective stops. Put cheap no-action checks before expensive enrichment, while preserving the data needed for exit management.

Acceptance: count requests and evaluation work per tick before/after; unchanged holdings do not repeatedly trigger equivalent enrichment; dashboard calls do not overlap indefinitely; all risk surfaces agree on committed exposure.

## Proposed product shape

One simple home screen with four primary views: Overview, Positions, Activity, and Performance. Settings and research detail stay secondary.

- Overview: separate stock and Bitcoin mode/venue/status; labeled period return after costs; current risk; next readiness blocker and an understandable next step.
- Positions: entry reason, current price with timestamp, position value, net/open P&L, confirmed protection, exit condition, holding age.
- Activity: plain-language event timeline, with pending, filled, rejected, expired, and skipped reasons. Repeated “already held” events collapse into a count.
- Performance: daily equity and drawdown, exposure/utilization, realized and unrealized returns, fees/slippage, and comparisons with relevant passive benchmarks over identical periods. Stocks and Bitcoin have separate evaluation cohorts.

For example: “Stocks: paper, collecting evidence. Bitcoin: paused, execution setup incomplete. Current blocker: performance evaluation requires repair.” Exact performance copy should come from the repaired ledger, not the inconsistent existing totals.

## Repair sequence and implementation acceptance

Goal: trustworthy paper execution and clear performance evidence before any live transition. Architecture: immutable order intents -> venue-aware execution/reconciliation -> canonical fill ledger -> versioned evaluation -> one dashboard snapshot.

1. **Execution integrity.** Change brain `order-retry.ts`, `trader-scheduler.ts`, engine decision routes/models/adapters, and relevant migrations. Preserve protection; make requests idempotent; handle unknown outcomes and stale intents; block unapproved entries locally and at the engine. Tests must cover delayed ACK, repeated decision ID, retry payload, pause, halt, partial fill, and restart. Acceptance: one intended trade creates one protected exposure with no silent failure state.
2. **Accounting and evaluation.** Change `audit-log.ts`, `go-live-gate.ts`, `metrics.ts`, `validation-gate.ts`, server status routes, and engine fill/history contracts. Unify ledger outputs, correct statistics against independent references, bind gate to evaluation cohorts, and require complete evidence. Acceptance: reports reconcile and no missing/stale input earns a pass. Recompute existing paper results before drawing profitability conclusions.
3. **Bitcoin paper workflow.** Add explicit venue/asset capabilities, market data routing, fees, precision, and 24/7 protection/reconciliation. Test the complete lifecycle in isolation. Acceptance: Bitcoin's first paper round trip is recorded correctly; its readiness does not inherit stock evidence. Venue choice should be settled before implementing a live Coinbase route.
4. **Operator UX and efficiency.** Change trader dashboard rendering, a consolidated snapshot endpoint, plain-English explanations, and refresh behavior. Use responsive layouts and verify with desktop/mobile screenshots once browser access is available. Acceptance: the five user questions in finding 9 are immediately answerable, all stale states are visible, and measured request counts fall.
5. **Evaluate the frozen system.** Run prospective paper observation with a fixed version and explicit fees/slippage assumptions. Compare against passive stock/BTC benchmarks and cash over the same interval. Report uncertainty, drawdown, exposure, and operating costs. Any later live pilot needs a separately chosen allocation and loss limits; a passing software test is not evidence of trading profitability.
